# Hydra v1.0.0 실행 Goal

상태: 실행용 지시 후보 · Revision: 6 · 2026-10-19

완성된 제품의 필수 사용자 창구는 원격 Codex다. workflow 조회·제어에는 qualified MCP를 사용하며,
프로젝트 연결은 PC/P17의 허용된 native caller→fixed CLI→동일 core 경로를 따른다. 어느 경우든
사용자의 로컬 앱 조작을 요구해서 원격 수용을 대신하지 않는다. 일반 요구사항은 native 질문
(객관식+자유 입력·주관식)을 우선 사용하고 답변 의미를 설계/TC에 연결한다. 준비 질문에
attempt를 만들지 않는다. Plan/Goal/예약 선택은 CS §3.1·§7을 따른다. 문서를 읽거나 일반 구현
요청을 받았다는 사실만으로 native Goal·예약을 생성하지 않는다.

Hydra 자체 개발은 현재 허용된 Codex·GitHub 개발 절차로 진행한다. 개발 중인 Hydra의 MCP,
검증·전달·정리 기능을 앞선 PR의 실행 선행으로 요구하지 않는다. 검증된 기능의 자체 사용은
기존 owner·작업·미확정 효과를 대사한 뒤 한 경로에서 수행한다. 제품 수용 조건과 이 개발
절차를 혼동하지 않으며 원격 기능의 미검증을 로컬 앱/fixture 성공으로 닫지 않는다.


이 파일은 사용자가 다음 goal에 사용할 지시다. 파일 작성 자체가 goal 생성이나 구현 재개는 아니다.
아래 지시는 사용자가 실제 실행을 위임한 시점의 현재 상태·권한과 함께 적용한다.

현재 준비 상태: [계획의 설계 시작 순서](plan.md#11-지금-먼저-닫을-설계와-구현-시작-조건)에 따른
전체 조작 계약의 [첫 후보 F01–F12](../../product/mvp-design.md#42-전체-기능-조작표)를 작성했다.
첫 질문/Pause/Resume 흐름과 그 선행 단위를 EX/CP/NC/WR 및 통합 검증에 상세화했다.
[계획 §1.4](plan.md#14-첫-흐름까지의-구체적인-구현-인계)는 호출 문맥 reader(A), 독립 project CAS(B),
실제 질문 원본 연결(C), 결정 적용과 좁은 continuation(D), 실제 왕복(E)의 순서와 소유를 정한다.
[변경 명세 P01–P18](changes/README.md)은 각 결과의 구현·TC·리뷰·회복 경계를 구체화한다.
Codex 세션과 GitHub 활용 계약은 해당 원본/기능의 역할을 지정한다.
native 원본의 실제 연결과 설치·운영 증거는 남아 있다. 아래 지시는 scoped 계약 검토·구현·
자격 확인을 이어가는 후보이며 설계 문서가 있다는 이유로 미지원 효과를 활성화하지 않는다.
기존 P01/P02의 소스 검증은 각 검증 기록에서 재사용할 범위를 확인한다. P02 저장 경계는
typed 명령 완료가 아니며, 기존 다섯 MCP 도구는 예정된 좁은 명령 경로를 대신하지 않는다.
설계 정합성 점검과 전체 실행 준비의 판정은 [검증 §10](verification.md#10-설계-인계-점검)을 따른다.

## 복사할 지시

전체 설계 개선의 결정과 미확인 경로는 [계획 §0](plan.md#0-자료조사에서-설계-개정과-실행-인계까지)를
먼저 읽는다. 현재 native writer/control/wake의 실제 자격은 미확인이다. 아래 Goal은 그 실증과
필요한 작은 구현까지 포함하는 실행 후보이며, 설계 문서 작성 완료를 실행 자격으로 사용하지 않는다.

Hydra가 사람이 정한 목적·기준·위임 안에서 여러 프로젝트의 개발을 스스로 이어가고,
Hydra 안에서 그 진행·판단·제어·근거를 확인할 수 있도록 v1.0.0을 구현하고 실제로 검증하라.
GitHub는 작업·설계·코드·전달 정본, Codex는 판단·세션·질문·예약의 주체, Hydra는 최소
소유권/admission과 외부 정본의 projection·명령 guard를 가진 control plane이다.

1. 실제 repository/base/head·dirty 변경·소유권·기존 Issue/PR·설치 상태를 대사하고 보존하라.
   기존 후보를 없애거나 새 작업을 중복 생성하지 말라. 현재 instruction과 저장소 lifecycle을
   따르고 구현 경로 하나를 정하라. 설계 묶음의 정확한 revision을 고정하고 독립 검토로
   책임·호환·구현 가능성의 모순을 해결하라. 기존 사람의 결정과 위임은 재사용하라.
2. 전체 기능의 조작표와 공통 상태/권한/정본 의미를 기존 소유 문서와 대조하고 이미 닫힌
   결정을 재설계하지 말라. Hydra 명령과
   Codex/GitHub 직접 변경을 구분하고, 질문의 답변·결정 적용·실행 재개를 합치지 말라.
   첫 흐름의 상세 계약을 검토한 뒤 W1a 사전 조사와 W1b 최소 조회로 실제 호출 주체·대상·권한을
   확인하라. 계획 §1.4의 A/B를 독립적으로 준비하고 C의 source 확인과 D의 순수 guard/fixture
   구현을 연결하라. 새 결정 경로에는 WR의 project-v2 최소 guard와 명시적 legacy source를
   사용하되 전체 WorkBinding 전환을 요구하지 말라. 필요한 최소 구현과 실제 qualification을
   교차 진행하고 W1b 전체 완료를 구현의 선행 조건으로 두지 말라. 계획 §1.2의 한 작업 흐름을
   증명하고 native 운영을 확대하되 독립 WR·검증·전달 보강은 그 O를 기다리지 말라.
   이 대화에서 tool을 사용할 수 있다는 사실은 standalone Hydra의 권한/연결 증거가 아니다.
   미지원이면 미충족 요구·지원 가능한 경로·결정 주체를 명시하고 독립 packet은 계속 진행하라.
   API 우회·별도 모델 서버·tracker/DB·scheduler를 몰래 추가하지 말라.
3. [계획 §1.6](plan.md#16-구현-단계와-선택-순서)에서 현재 선행 능력을 충족한 작은 결과를 선택하고 해당 change spec과 소유 계약을
   직접 읽어 기존 작업과 연결하라. 번호순으로 무조건 실행하거나 모든 spec을 다시 작성하지 말라.
   이미 충족된 결과는 기존 증거로 재사용하라. 한 PR의 구현 owner와 독립 검토자를 분리하고,
   공유 writer 경계에서 직렬 통합하라. 실제 diff가 너무 크거나 결과가 독립적이면 목적·검증을
   보존해 PR을 분할하며 계획 숫자를 채우기 위한 PR은 만들지 말라. 세션을 넘는 일에는 durable Issue를
   재사용하거나 등록하되 번호·제목·template을 사용자의 입력 조건으로 강제하지 말라.
   기존 설계가 충분하면 그대로 실행하고, 부족한 부분만 목적·책임·동작·실패/복구·완료·
   범위로 보완하라. 외부 제안의 유용성과 실제 실행 권한을 구분하라.
   같은 기능의 여러 PR은 기존 spec을 재사용하고 각 단계의 요구·범위·TC·완료를 고정하라.
   버그가 계약 위반이면 구현과 회귀 TC를 고치고, 계약 자체 변경이면 기존 명세를 먼저 개정하라.
   독립적인 목적·책임·완료 기준이 필요한 경우에만 새 spec을 작성하라. P13의 증거 수집·CI와
   좁은 검증 실행, P14의 독립 main CI 보존과 보호 전달은 같은 명세의 별도 구현 단계다.
   계획 §0.2의 G1–G4로 실제 결과를 연결하라. P10은 필요한 관계 준비를 끝까지 조정하고
   P11의 읽기와 혼동하지 말라. P14는 연속 main push의 exact merge SHA 검증을 보존하라.
   P08은 발견·제안, 위임 작업, 복구를 구분하며 같은 근거의 제안/질문을 반복 생성하지 말라.
4. 사용자 예시를 전체 시나리오로 취급하지 말라. 각 경계의 다양한 입력, 출처/권한,
   진행 중 변경, 중복/유실, 동시성, 부분 실패, 모델 오판, 악성 내용, 복구·정리를 먼저
   도출하라. 유용한 요구와 공격이 섞여도 유효한 사실을 살리되 텍스트로 권한·명령·평가
   기준을 바꾸지 말라. 과도한 거절이나 반복 질문으로 정상 진행을 막는 것도 결함이다.
5. 요구로부터 독립적인 oracle과 TC를 만든 뒤 구현하라. D는 결정적 TC/CI, L은 고정 사례와
   독립 판단 평가, O는 실제 외부/설치 환경의 관측으로 검증하라. 의미 있는 RED→GREEN과
   영향 회귀를 확인하고, 새 변경/실패/미해결 우려가 없으면 불필요한 반복 검사 대신 전달하라.
   기존 유효한 코드·TC·설계는 재사용하며 테스트 수나 LLM 성공 보고로 완료를 대신하지 말라.
6. 세션 계약에 따라 주관 task가 목표와 남은 책임을 유지하고, PR 구현·독립 검토에 필요한
   최소 역할만 배정하라. 같은 책임·소유·문맥이 유효하면 task를 재사용하고, fork/compaction이
   권한·실제 실행의 이전이나 완료 증거라고 가정하지 말라. task 생성·다른 task 메시지·예약의
   실제 도구 조건을 지키며, 일반 Goal 위임으로 도구별 명시 조건을 우회하지 말라.
   P17의 연결은 위임이 아니며 P18의 실제 범위 변경·철회·취소를 원래 책임에 적용하라.
   Stop·Issue close·원본 접근 실패를 취소나 권한 부여로 합성하지 말라.
   작업·세션·질문·예약·자원 identity를 정확히 연결하라. 재시작/응답 유실은 원본을 먼저
   대사하고 같은 효과를 맹목적으로 반복하지 말라. 자체 progress가 무한 wake를 만들지
   않게 하며 기다리는 작업 때문에 독립된 허용 작업이 정체하지 않게 하라.
7. 각 PR에서 목적 기반 TC·관련 CI를 함께 구현하고 독립 명세/코드/보안 검토를 마친 뒤
   exact final head/base로 전달하라. P13이나 최종 통합까지 검증을 미루지 말라. source 코드가
   병합돼도 해당 spec의 필수 live 증거가 없으면 기능 단위를 완료시키지 말라.
   기존 보호를 우회하지 말고 필요한 사람의 승인에는 원본 링크와 정확한 대기 이유를
   남겨라. 시각적으로 의미 있는 최종 PR을 공개하기 전 실제 running screen을 보여라.
   merged·main 검증·설치·운영을 각각 확인하라. 배포는 해당 목표의 위임 범위 안에서만 하라.
   [자체 개발 복구 절차](changes/README.md#51-hydra-자체-개발의-진행과-복구)에 따라 실패한
   CI는 같은 PR에서 수정하고, merge ACK 유실은 원래 결과를 조회하며, main 실패는 원래 책임의
   복구 PR로 연결하라. 완료되지 않은 Hydra adapter의 제한으로 기존 허용 개발 도구까지 막지 말라.
8. P16의 화면 구현과 전체 v1 수용을 구분하라. 새 제품 diff가 없는 실증을 위해 형식적인
   PR을 만들지 말고 실제 증거를 원래 작업에 연결하라. 서로 다른 설계/컨벤션/검증을 가진
   일반 프로젝트 두 개로 전체 흐름과 장애/복구를
   검증하라. 특정 제품에 맞춘 core 분기나 다른 제품에 대한 의존을 추가하지 말라.
   Hydra 자체 등록이 없으면 현재 저장소 개발 절차로 구현하며 self-use를 위조하지 말라.
9. 목표 종료 시 요구별 증거와 실제 종료·보존·정리를 확인하라. 닫힌 Issue의 pending
   책임도 재발견하고 foreign/dirty/active/unknown 자원을 보존하라. 무의미한 예약/세션은
   지원되는 owner 경로로 종료·보관하며 새 상시 운영을 자동 위임하지 말라.

자율 진행할 일은 구현 세부 선택·TC·복구·리뷰 수정이다. 질문할 일은 아직 정해지지 않은
목적/taste/정책/권한/중요한 외부 효과다. 같은 승인 요청을 반복하지 말고 구체적 결정,
준비된 선택지·영향·원본 링크를 제시하라. 필요한 결정을 기다리는 동안 독립 작업은 계속하라.

최종 결과는 R01–R16의 D/L/O 상태, 실제 revision과 CI/리뷰/merge/main/설치·운영 근거,
남은 책임을 기존 작업에 연결해 보고하라. PASS/FAIL/NOT RUN/BLOCKED를 구분하라.
필수 native/운영 증거 없이 source ready를 전체 v1.0.0 완료로 표시하지 말라. 전체 요구가
충족되면 goal을 완료하고 선택 개선을 이유로 작업을 무한 연장하지 말라.
