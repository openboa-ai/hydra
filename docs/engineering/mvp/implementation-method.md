# Hydra v1.0.0 구현·TC·CI 기준

상태: 설계 후보 · Revision: 3 · 2026-10-19 · 관련 작업: Issue #3

[v1.0.0 제품 설계](../../product/mvp-design.md)의 기능을 안정적으로 구현하기 위한 기준이다.
제품의 목적과 기능별 여섯 항목 설계를 먼저 사용한다. 이 문서는 구현 방식의 후보이며,
전체 상세 설계의 수용, 코드 구현, 테스트 실행 또는 CI 적용 완료를 뜻하지 않는다.

제품이 실제로 운영할 정본·projection·명령·시나리오와 구현 단위는
[SDLC 통합 설계](../../architecture/sdlc.md)를 따른다. 이 문서는 그 단위를 구현하는 방법을 소유한다.
실제 PR 단위는 [변경 명세 목록](changes/README.md), 의존 순서와 Goal 경계는 [구현 계획](plan.md)을
따른다. 방법론의 수용은 개별 미수용 설계·외부 효과의 권한을 자동 생성하지 않는다.

## 1. 구현에 넘길 작업 단위

작업 하나는 독립적으로 관측·검증할 수 있는 결과를 제공한다. 구현 에이전트는
전체 제품의 목적을 다시 결정하지 않고도 아래 정보로 작업할 수 있어야 한다.
명세는 기능·변경의 정본이고 PR은 그 계약을 전달하는 결과 단위다. 같은 명세의 여러 구현 단계는
각각 PR로 검토할 수 있다. 재사용·개정·새 명세의 기준은 [변경 규약 §1.1](changes/README.md#11-명세-재사용개정과-새-명세의-경계)을
따른다. PR 분할 때문에 명세를 복제하거나, 충분한 기존 계약을 양식에 맞추어 다시 쓰지 않는다.

| 필수 내용 | 작성 기준 |
| --- | --- |
| 목적·연결 | 해당 제품의 요구사항·경험에 기여하는 목적; Hydra 자체 개발은 S1–S6에 연결 |
| 수용한 설계 | spec 경로·고정 revision·해당 구현 단계/요구, 목적/책임/동작/실패·복구/완료/범위 |
| 입력과 출력 | 후속 작업과 공유하는 타입·필드·오류 의미·호환 조건 |
| 변경과 소유 | 수정할 코드·시험 경로, 기존 의존 요소, 허용된 작업 공간·자원 |
| 결정적 TC | 테스트 ID, 사전 상태, 입력/사건 순서, 기대 결과, 금지 효과 |
| 검증 절차 | 실제 실행 명령, 필요한 환경, 예상 성공·실패, 통합 시험 범위 |
| 판단 평가 | LLM 평가가 필요한 동작, 고정된 기준 사례와 독립 검토 방법 |
| 완료 증거 | PR 병합·기능 활성화·명세 전체 완료 조건을 구분한 해당 revision의 증거와 후속 책임 |

공유 인터페이스와 수용 조건은 구체적으로 정한다. 내부 함수 몸체와 모든 구현 코드를
계획에 미리 쓰지는 않는다. 구현자는 그 계약 안에서 자료구조·알고리즘·가역적 코드
구성을 선택한다. producer/consumer가 서로 다른 타입·오류 의미를 가정하는지 작업 배정
전에 대조한다. 비공개 함수나 파일별로 독립 리뷰를 강제하는 분해는 피한다.

배정 brief는 해당 작업의 목적·수용 spec/revision, 변경 소유 경로, 필요한 producer/consumer,
현재 미확정 효과·제약, TC/명령·예상 결과, 반환할 diff·증거·남은 책임으로 제한한다. 전체 대화나
무관한 private 연구를 복사하지 않는다. 구현자가 원문과 의존 계약을 읽을 수 있는 링크를 준다.
별도 ledger를 만들지 않고 기존 Issue/PR·Codex 작업의 원본 연결을 재사용한다. 재진입 시 완료
표시만 보지 않고 실제 revision·증거·pending 효과를 대조하여 중복 구현·재배정을 막는다.

### 기존 설계에서 구현 작업을 도출하기

Hydra가 다른 프로젝트의 개발을 수행할 때도 이 원칙을 적용한다. 먼저 해당 프로젝트의
수용된 설계 정본·revision·위임 범위를 확인하고, 관련 아키텍처·의존 계약·기존 구현·TC를
함께 읽는다. 구현자가 받은 요약만으로 원래 제약을 대체하지 않는다. 문서가 존재한다는
사실만으로 수용이나 실행 권한을 추정하지 않으며, 기록된 수용 결정은 재사용한다.

기존 작업 기록에서 `요구사항 참조 → 작업 → TC/평가 → 구현 revision → 결과 증거`를
연결한다. 원문 ID가 없으면 문서 경로·revision·section으로 참조한다. 별도 운영 대장이나
설계 복제본은 요구하지 않는다. 구현 증거가 있는 요구, 코드만 있는 요구, 미구현 요구,
현재 확인할 수 없는 요구를 구분한다. 코드나 완료 표시만 있고 필요한 증거가 없으면
그 요구의 다음 행동은 재구현이 아니라 현재 상태의 검증일 수 있다.

다음 작업의 계약이 충분하면 바로 작업·TC·구현으로 진행한다. 요구사항을 바꾸지 않는
자료구조·내부 함수·시험 구성 선택은 에이전트가 해결한다. 실제 모순이나 중요한 공백은
관련 원문, 재현 사례, 영향받는 요구·작업, 권고 변경안을 남긴다. 외부 동작·공유 인터페이스·
성능 및 실패 보장·범위·권한·완료 기준이 바뀌면 설계 변경으로 다룬다. 가역적 변경도
이 경계의 예외가 아니다. 사람의 판단이 필요한 결정은 기존 위임 경계에 따르고
무관한 작업은 막지 않는다.

세션을 다시 열거나 설계 revision이 바뀌면 기존 기록과 현재 사실을 대조한다. 고정된
설계를 조용히 최신 문서로 바꾸지 않는다. 프로젝트의 변경·대사 계약에 따라 영향받는
작업과 증거를 재평가하고, 유효한 기존 구현·증거는 보존한다. 변경안을 몰래 구현하거나
현재 코드에 맞춰 제품 설계·acceptance를 약화하지 않는다.

이 경로의 최소 검증 사례는 다음과 같다. 참조·revision·중복 효과는 결정적으로 검사하고,
설계 해석과 작업 분해의 타당성은 독립 검토·평가로 확인한다. 문서 연결만으로 의미적
충족을 증명하지 않으며 실제 실행 사례에서 끝까지 연결되는지도 확인한다.

| 사례 | 기대 결과 |
| --- | --- |
| 충분한 설계·미구현 요구·유효한 위임 | 원래 설계와 기준을 유지하며 의존 순서에 맞는 작업과 TC를 도출하고 구현 진행; 불필요한 설계 재작성·재승인 없음 |
| 계약을 만족하는 기존 구현과 유효한 증거 | 완료 부분을 보존하고 다음 미충족 요구 선택; 중복 작업·PR 생성 없음 |
| 구현은 있으나 증거가 없거나 오래됨 | 필요한 검증을 수행하고 결과에 따라 수정 여부 결정; 자동 완료·전면 재구현 없음 |
| 제품 동작에 영향을 주지 않는 구현 선택 | 에이전트가 결정하고 진행; 사용자에게 내부 구현 선택을 떠넘기지 않음 |
| 두 설계의 실제 모순 또는 중요한 공백 | 충돌 근거와 영향·변경안 제시; 영향받는 실행을 보류하고 독립 작업 진행 |
| 실행 도중 설계 변경 또는 세션 재개 | 기존 작업과 revision 대조, 필요한 재평가 수행; 오래된 증거로 변경된 요구를 완료 처리하지 않음 |
| TC는 통과하지만 필수 요구가 누락되거나 의미가 변형됨 | 독립적인 설계 충실성 검토에서 미완료 판정; 기준을 낮추지 않고 작업·검증 보완 |
| 문서 구조와 용어가 서로 다른 두 프로젝트 | 각 정본·요구사항 참조·평가 기준을 유지하며 같은 실행 원리 적용 |

## 2. 테스트 가능성과 복구를 위한 구현 구조

- **판단과 효과의 경계:** 현재 사실을 받아 허용된 전이·행동 후보를 만드는 코드와,
  GitHub·파일·세션 등 외부 효과를 수행하는 코드를 분리한다. LLM의 행동 제안도 같은
  실행 전 확인 경계를 통과한다. 제안 결과가 실행 권한이 되지 않는다.
- **명시적 결과:** 성공, 실제 실패, 대기, 관측 불가를 타입 또는 검증된 record로 구분한다.
  빈 값이나 timeout을 성공·종료로 바꾸지 않는다. 예외를 잡고 원인을 지우지 않는다.
- **단일 소유:** 같은 변경 대상의 writer와 공유 계약의 통합 책임을 명확히 한다.
  독립 조사는 병렬화할 수 있지만 공유 파일·프로세스·DB·포트의 충돌을 방치하지 않는다.
- **효과의 복구:** 재실행 가능한 효과, 먼저 실제 상태를 조회해야 하는 효과,
  중단해야 하는 효과를 설계에서 구분한다. identity·의도·read-back·재시도 상한을 연결한다.
- **시간과 순서:** 시계·대기·난수·provider 응답을 교체 가능한 경계로 두어 실패를 재현한다.
  임의 sleep 증가로 경합을 숨기지 않는다. 실제 OS/프로세스 의미는 별도 통합 시험으로 확인한다.
- **관측 가능성:** 단계별 입력의 안전한 식별자, 상태, 오류 분류와 효과 결과를 확인할 수 있게 한다.
  로그에 자격 정보·private 원문·비밀값을 넣지 않고 필요한 사실만 기록한다.

기존 구현을 이 기준으로 평가하고 필요한 책임 경계부터 개선한다. 큰 파일이라는 이유만으로
전면 재작성하지 않는다. 테스트 가능한 접점이 없을 때에는 먼저 작은 구조 변경과 동작 보존
검증을 설계한다. 새로운 실행기나 상태 저장소를 기본 해결책으로 삼지 않는다.

## 3. 구현 반복: 기대 결과에서 시작하기

```mermaid
flowchart LR
  S[수용한 요구·상세 설계] --> T[독립적으로 도출한 TC]
  T --> R[의도한 실패 확인]
  R --> I[필요한 구현]
  I --> G[TC와 관련 회귀 통과]
  G --> F[구조 정리 후 재검증]
  F --> V[독립 검토·통합·최종 후보 CI]
  V --> E[revision에 연결한 완료 증거]
```

새로운 결정적 동작과 결함 수정은 기대 결과를 먼저 고정하고 실패 신호를 확인한 뒤 구현한다.
실패는 목표 동작의 부재 또는 결함 때문에 발생해야 한다. 의존 패키지 누락·오타·실행 환경
오류를 회귀 재현으로 세지 않는다. 이미 충족된 동작의 테스트는 기존 보존 증거로 분류한다.
RED는 그 TC를 실패시킬 실제 제품 결함을 설명할 수 있어야 한다. 권한 없는 효과 차단 시험도
다른 guard는 유효하게 두고 같은 진입점의 허용된 정상 진행을 함께 확인한다.

TC는 현재 구현의 반환값을 복사하거나 테스트 대상 함수를 다시 호출해 기대값을 만들지 않는다.
정상 결과뿐 아니라 금지된 외부 효과와 남겨야 할 책임도 확인한다. 구현 후 같은 TC를 통과시키고
관련 회귀와 통합 영향을 검사한다. 통과 이후 가독성·중복·책임 경계를 정리하고 재검증한다.
기대 결과를 변경하려면 요구사항의 정정인지, 잘못 작성한 TC인지 먼저 설명한다.
GREEN은 목적을 충족하는 최소 변경이다. fixture 값에만 맞춘 hardcode, 모든 호출 거절,
timeout 증가·검사 삭제로 실패를 숨긴 구현은 통과가 아니다. 인접 책임에 변화가 필요하면 실제
영향을 설명하고 같은 수용 경계 안에서 수정한다. 무관한 재작성은 함께 넣지 않는다.

기존 작업은 보존한다. 과거 결함의 회귀력을 확인할 필요가 있으면 격리된 이전 revision 또는
통제된 결함 주입으로 실제로 실패하는지 확인한다. 작업 중인 checkout을 덮어쓰거나 기존 코드를
삭제해서 TDD 이력을 만들지 않는다. 문구 수정에 형식적인 테스트를 추가하지 않으며,
설정·CI 변경에는 그 동작을 확인할 파서·계약·통합 검사 중 적합한 검증을 선택한다.

## 4. 결정적 TC의 깊이

| 시험 종류 | Hydra에서 확인할 것 | 기대 결과의 근거 |
| --- | --- | --- |
| 상태·판단표 | 중단 원인, 실행 허용, 실제 실행, 전달, 정리 책임의 구분 | 기능별 상태 계약·불변조건 |
| 경계값·오류 입력 | 상한 직전/정확한 상한/초과, 누락·손상·모순 입력 | 명시된 입력 계약과 실패 의미 |
| producer/consumer 계약 | 실제 반환값이 다음 계층에 전달됐을 때 행동·표시의 일치 | 양쪽이 공유하는 인터페이스 |
| 순서 변화 | 중복 callback, 늦은 결과, 역순 관측, 취소와 결과 도착의 경합 | identity·소유권·전이 규칙 |
| 효과와 복구 | 요청 후 응답 유실, checkpoint 전후 종료, 재시작 후 대사 | 기록·read-back·재시도 계약 |
| 프로젝트 격리 | 서로 다른 검증 정책·scope·대기 조건, 무관 입력의 증가 | 공통 연동 계약과 프로젝트 고유 기준 |
| 공개 경계 | 비밀값·private 문맥이 공개 결과·로그로 흐르지 않음 | 데이터 분류와 공개 payload 계약 |

외부 응답을 통제하는 test double은 사용할 수 있지만, 그 mock이 호출됐다는 사실만으로
제품 동작을 증명하지 않는다. 실제 adapter와 consumer를 연결하는 계약 시험, 임시 Git 저장소,
필요한 실제 프로세스 시험을 함께 둔다. 운영 자격이나 유료 모델 호출은 결정적 테스트에서 요구하지 않는다.

생성형/stateful 테스트를 사용하는 경우 seed와 실패 사건열을 보존한다. 기준 모델은 대상
구현과 독립적이어야 한다. 모든 조합을 무작정 열거하지 않고 요구사항이 만드는 경계와
순서 변화에 집중한다. 테스트 수·라인 커버리지만으로 충분성을 판정하지 않는다.

## 5. 디버깅과 반복 패치의 중단 조건

오류가 나면 관측한 현상과 기대 결과를 비교하고, 재현 조건·실제 데이터 흐름·최근 변경을
확인한다. 어느 책임 경계에서 계약을 위반했는지 찾고 하나의 원인 가설을 검증한다.
그 원인을 재현하는 회귀 사례와 실제 수정의 효과를 함께 확인한다.
기존 작업 기록에는 관측/예상 차이→원인 가설→가설을 구분하는 실험→결과→수정/기각을 짧게
연결한다. 여러 경계를 넘는 문제는 각 경계의 실제 입력·결과를 안전한 범위에서 관측한다.
로그를 늘린다는 이유로 환경 변수·credentials·private 원문을 덤프하지 않는다.

환경 문제와 제품 결함은 구분해 기록한다. 재현이 안 되면 필요한 관측을 추가하며,
검증되지 않은 추측을 여러 패치로 쌓지 않는다. 같은 원인의 결함이 두 수정 검토에서
반복되는 경우를 진단 전환 신호로 삼고, 누락된 계약·TC·다른 영향 경로를 다시 검토한다.
명백한 구조적 누락은 횟수를 채우지 않고 즉시 처리한다.

이는 실패를 무시하거나 보호 검사를 우회하는 상한이 아니다. 가역적인 내부 설계 수정은
에이전트가 해결하고, 제품 기준·scope·권한 변경은 구체적인 영향과 함께 판단 대상으로 올린다.

## 6. CI 설계와 실행 시점

| 시점 | 검사 | 결과가 보장하는 범위 |
| --- | --- | --- |
| 구현 반복 | 해당 TC, 인접 회귀, 필요한 계약 시험 | 현재 수정의 빠른 피드백 |
| 검토 가능한 후보 | 해당 변경의 전체 필수 suite, 타입·빌드·정적 검사 | 후보의 결정적 요구와 통합 적합성 |
| 최종 PR/merge 후보 | 요구사항별 TC 매핑, 보호된 CI·보안 검사, 정확한 head/base의 필수 리뷰 | 실제 전달할 revision의 승인된 검사 |
| 모델·prompt·skill 판단 변경 | 고정 사례 평가와 독립 판정, 평가 환경 기록 | 그 판단 변경에 대한 행동 품질 |
| 설치·전달 및 운영 경계 변경 | 필수 실제 환경 S1–S6 시나리오, main 확인·복구·정리 증거 | 해당 설치와 관측 범위의 실제 동작 |

현재 Python CI의 명령은 `python3 -m unittest discover -s tests -v`다. Mac app에는
별도의 frontend test/build 및 Rust test/build가 있다. 실제 구현 계획은 그 시점의
workflow와 허용된 로컬 자원 실행 경로를 다시 확인하고 정확한 명령·환경·예상 결과를 적는다.
여기서 명령을 적은 것은 실행한 것이 아니다. 기존 필수 검사·CODEOWNER·보안 검사를 유지한다.
각 PR은 자신의 TC와 회귀를 함께 제공한다. [P13](changes/13-verification-evidence/spec.md)은
요구와 증거의 연결·수집·평가 장치를 보강하는 PR이며 앞선 PR의 TC를 마지막으로 미루는 단계가 아니다.

결정적 suite는 깨끗한 환경에서 재현 가능해야 하며 필수 검사를 생략해 녹색으로 만들 수 없다.
fixture·dependency·seed·실행 시간 제한을 명시하고 실패·skip·환경 제한을 보고한다.
flaky 테스트는 원인을 추적한다. rerun으로 통과한 결과만 골라 최초 실패를 숨기지 않는다.

수정 중에는 좁은 검사를 빠르게 돌리고, 최종 후보에는 필요한 전체 검사를 수행한다.
새 변경·실패·해소되지 않은 영향이 없으면 같은 전체 검사를 이유 없이 반복하지 않는다.
반대로 변경된 범위를 검사하지 않은 과거 결과로 최종 후보를 대체하지 않는다.

TC·요구사항 ID의 연결 검사는 누락을 찾지만, TC가 실제 의미를 검증하는지는 독립 검토가
판단한다. critical invariant에 대해서는 선택적으로 결함 주입이나 이전 revision 재현으로
시험의 탐지력을 확인한다. 형식적 매핑만으로 완료 판정을 자동화하지 않는다.

LLM 평가는 모델·prompt·도구·사례·rubric revision과 반복 조건을 기록한다. 호출 비용과
자격이 필요한 실행은 승인된 환경에서만 수행한다. untrusted PR에 비밀값을 전달하지 않는다.
일반 CI의 고정 응답 fixture는 평가 장치의 동작을 검증할 뿐 실제 모델의 판단 품질을 증명하지 않는다.
필수 live 평가가 실행되지 않으면 NOT RUN/BLOCKED를 유지하고 준비 완료로 올리지 않는다.

## 7. 검토·병렬화·통합

구현자의 자체 점검 뒤 독립 검토자는 수용한 요구와 실제 diff·시험 결과를 대조한다.
먼저 명세 충실성에서 요구 누락·범위 확대·실패 의미·금지 효과·정상 진행을 확인하고, 품질·보안에서
책임 경계·복구·테스트 탐지력·공개/권한 경계를 확인한다. 한 검토 기록에 담더라도 두 판정 근거는
구분한다. 구현자의 자체 점검을 독립 검토로 세지 않으며 고정된 모델·인원·리뷰 횟수를 강제하지 않는다.
작업 단위의 범위가 작아도 그 변경이 깨뜨릴 수 있는 입력·상호작용은 검토 대상이다.

공통 타입이나 상태 의미가 바뀌면 consumer까지 같은 후보에서 검증한다. 의존 작업은
선행 인터페이스가 정해진 뒤 진행하고, 병렬 구현은 실제로 분리된 소유 공간·자원과 통합
책임이 있을 때만 선택한다. 현재 실행 계약의 동시성 제한은 별도로 준수한다.
공유 파일을 수정하는 작업은 원칙적으로 순서를 정한다. 병렬 분석이나 분리된 변경을 통합한 뒤에는
각 담당자의 PASS를 합산하지 않고 실제 합쳐진 후보의 producer→consumer 흐름과 전체 영향 회귀를
검사한다. 최종 독립 검토는 전체 PR/통합 diff에서 개별 검토가 놓친 상호작용도 확인한다.

review 수정은 같은 책임 아래 원인을 묶어 반영한다. 수정된 부분과 영향 경계를 재검토하고,
필수 final-head 리뷰 및 검사를 보존한다. 리뷰 횟수나 시간 부족을 이유로 미해결 결함을
임의로 완료 처리하지 않는다. 에이전트의 완료 보고는 실제 diff와 실행 결과로 확인한다.

## 8. 작은 단위의 구체적인 예

예시: **늦은 checkpoint가 현재 실행을 덮어쓰지 않게 한다.**

- 목적: C4/C6, S4의 실행 소유권과 복구 책임 보존.
- 설계 입력: 같은 작업의 이전 step A, 현재 step B, 늦게 도착한 A 결과와 현재 head.
- 기대 결과: A 결과를 stale로 식별하고 B 상태·소유권을 유지한다. 새 commit·PR·merge·
  자원 해제 효과가 없어야 한다. 같은 A 결과를 반복해도 상태가 달라지지 않는다.
- 양성 사례: 유효한 B 결과는 정확히 한 번 소비되고 후속 단계에 연결된다.
- 시험: 실제 native checkpoint 경로와 상태 저장/효과 경계를 연결하고 전후 상태 및
  외부 효과 목록을 비교한다. identity 판정 함수의 단위 테스트만으로 완료하지 않는다.
- 실패 처리: 조회가 불가능하면 B 종료를 추정하지 않고 기존 책임을 보존한다.
- 완료 증거: 해당 행동을 깨는 변경에 실패하는 TC, 수정 후 통과, 관련 회귀·계약 시험,
  독립 검토와 최종 후보 검사. 실제 native 재시작 자격은 별도 운영 증거로 남긴다.

이 예시는 기준의 적용 예다. 실제 작업으로 배정할 때는 현재 소스에서 정확한
파일·함수·테스트 위치와 명령을 고정한다. 기존에 충족된 동작이면 중복 구현하지 않는다.

## 9. 단위 완료와 v1.0.0 완료

단위 완료에는 수용한 설계, 요구사항별 결과, 현재 revision, 필수 검사와 독립 검토,
알려진 제한 및 후속 소비자 연결이 필요하다. 기존 실패나 미실행 검사는 이름과 이유를 남긴다.
local PASS, 원격 CI, 리뷰, 보호 병합, 설치, 실제 운영은 서로 다른 결과다.

v1.0.0 완료는 개별 단위의 합계가 아니라 상위 S1–S6가 실제로 연결됐는지로 판정한다.
중요한 제품 선택을 구현 중 새로 발명해야 한다면 그 부분은 상세 설계로 돌아간다.
새 기능이나 무관한 정리는 현재 구현 단위에 자동으로 추가하지 않는다.
